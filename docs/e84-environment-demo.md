## 実機確認：主要動線を確認、残試験あり

- E84への通常flash書き込み・271664 bytesの照合とCYBOOT_SUCCESSを確認。eFuse・ライフサイクル・KitProg3の更新なし。初回はKitProg3未接続で停止し、ユーザーのJ1接続後に成功。
- iPhone 17／iOS 27.0.1へ、既存署名設定で環境対応Releaseを更新インストール・起動。署名検証成功。アンインストール・既存記録削除なし。
- 実機DBはv6→v7へ移行。更新前後でhealth_records／onboarding_completions／reminder_preferences／scan_preferencesのテーブル定義・全行全項目が一致。quick_check正常・foreign_key_check違反なし。一時DBコピーは照合後に削除し、健康値は出力していない。
- UIはユーザーの操作・目視回答で確認。ライブ温湿度、正常15秒後の環境保存・SHT40／受信日時、履歴から同じ値・日時、手動／完了LEDの点灯・消灯を確認したと回答。
- ユーザーは機内モードON・Wi-Fi OFF・Bluetooth ONで2回とも保存・履歴・LED成功、途中取消で履歴増加・20秒後までの遅れた点灯なし、今回の環境値付き試験記録1件の削除と他の履歴表示も確認したと回答。
- 試験後DBはquick_check正常・foreign_key_check違反なし・孤立環境行なし・availableの保存行あり。一時コピーは削除。実値は出力していない。
- 「表示とDBの不一致」と扱っていた点は訂正。提供スクリーンショットは取得成功の過去記録を開いており、上部は現在のキット未接続状態、下部は計測時の保存環境だった。DBのavailableと一致し、この画面に保存矛盾はない。混同を防ぐため、結果上部に「現在のキット接続・LED状態」と保存環境の説明を追加し、環境欄を「計測時に保存したキット付近の環境」へ変更。表示修正後も全324テスト・解析・署名ビルド・codesign検証が成功し、同じbundleへ更新導入・起動済み。実画像・実値・日時はリポジトリに保存しない。
- 取得OFFの未測定保存はDBに存在する。取得ON＋未接続を終了時に固定したdisconnected行は実機から採取できていないため、そのケースのDB永続化は実機未確認として残す（自動試験は成功）。同じ操作の再確認はここで止める。
- 実機の全受け入れ項目合格は未宣言。強制障害・UART照合・参考計器比較等は未確認。

## 実装

- 設定の既存キット接続を共用し、「環境情報を取得する」を明示的にオンにする。起動時はOFF。LEDの自動連動は別のスイッチで、連動OFFでも環境取得できる。
- 前景で約2秒ごとに1件のRead。LED送信・点灯中は新規Readを休止し、消灯指示を優先する。長いReadを重ねず、2秒timeout時は接続を破棄する。
- 正常・初期化中・センサーエラー・範囲外、接続なし・OFF・未対応・期限切れ・Read失敗を区別する。期限切れは「更新が停止しています」とし両値を未測定にする。
- 計測終了時、Readを待たず最新ペアと鮮度を固定。健康記録を先に保存し、環境保存はアプリ所有の別処理で続ける。保存失敗時は「チェックは保存済みです。環境情報を保存できませんでした」と表示し、健康記録を再INSERTせず固定値で再試行する。
- 結果と履歴から開いた結果に、保存時の室温・相対湿度・SHT40由来・iPhone受信日時を表示。体温と分離。取得できなかった値はNULL。関連行のない旧記録は「環境情報の保存なし」で、理由を推測しない。保存済みの値は経過時間で失効させない。
- SHT40はキット付近の1サンプル。15秒平均、体温、部屋全体の代表値、校正済み温湿度計、医学的判断として扱わない。健康値をキットへ送らず、クラウド接続を追加しない。

通信の正本は [environment-protocol.json](../firmware/e84/environment-protocol.json)、確定事項は [implementation-decisions.md](implementation-decisions.md)。ファームウェアの再現・復旧は [environment/README.md](../firmware/e84/environment/README.md)。Infineonの [SHT4x API](https://github.com/Infineon/sensor-humidity-sht4x/blob/6a5b9edc72615746852fe3fcb1ecff97c36a3e94/api_reference.md) と [Driftの移行手順](https://drift.simonbinder.eu/migrations/) を参照した。

## DBの保護

このブランチはv4だったため、実機で確認済みの `codex/fix-startup-db-migration` のv6修正を先に取り込んだ。UI全体のmain取り込みは行っていない。v7で任意関連テーブルを追加し、v4のscan_mode列が既存でも正しい定義なら保持する。想定外の定義や、旧版に既に環境テーブルがある場合は自動修復せず、トランザクションを戻して既存記録を保護する。

日時、NULL、自己申告、体温、レポート、説明確認、通知・研究設定を保持する。環境行の親は存在確認＋外部キー＋CASCADEで保護し、削除後の遅い関連付けから親を再作成しない。実機更新時にDBを一時コピーし、v6→v7移行前後の全項目保持を値を表示せずに照合した。端末記録は削除していない。一時コピーは確認後に削除済み。v7導入後に旧v4アプリへ戻す運用は保証しない。

## 次に実機試験する場合の順序

1. 最新mainの画面を統合するか、このブランチの画面を使うか決める。実機の記録を残して起動・履歴を確認する。アンインストール／DB削除で移行問題を回避しない。
2. 復旧用LEDイメージを保持し、環境対応ファームウェアを通常flashへ書く。SHT40単体取得と、Read＋IAS共存を先に確認する。
3. iPhoneで接続して環境取得をオン。実際の室温・湿度・更新状態を確認。LED連動は必要なら別途テスト・目視確認してオンにする。
4. 顔位置確認→15秒→健康保存→環境保存→結果→履歴から同じ値の再表示を確認する。切断・OFFでも通常の健康チェックが成立することを確認する。
5. E01〜E12と設置影響を記録し、セットアップ後にWi-Fi／モバイル通信OFF・Bluetooth ONで最低2回繰り返す。個人の健康値や顔画像を試験ログ・Gitへ含めない。
