## 提案1：計測の所有権

C側の計測セッションが実計測の唯一の時計を所有し、B側はCが通知する状態・経過時間を描画する方式を提案する。B側の別タイマーで計測終了を決めない。

状態の候補：準備中 → 顔位置調整 → 計測中 → 完了、または失敗／中断。

顔・明るさ確認前は計測時間を進めない。開始前のpermissionDenied / faceNotFound / poorQualityと、計測開始後のinterruptedを区別する。B側は画面離脱・アプリ非アクティブ時にキャンセルを通知し、C側がフレーム処理・タイマーを停止／解放する。キャンセル完了後に古い完了通知で画面が成功状態へ戻らない契約が必要。

未合意：セッションAPI名、状態通知の形式、キャンセルの完了条件、顔外れの判定猶予、複数顔の扱い、品質閾値。

## 提案2：共有型

仕様のHealthCheckResultを基に、次をB/C共同で定義することを提案する。現時点でDartの共有型は作らない。

- 計測結果：ID、計測日時、実経過時間、顔検出状態、品質、nullableな実験特徴量とその出典。
- 開始前失敗：権限拒否／顔未検出／品質不足。計測結果と別に表現する候補。
- 途中中断：理由と実経過時間。固定15秒の成功結果へ変換しない。
- 自己申告：任意の体調1〜5、任意の外部由来体温と出典。
- レポート：本文、実際の生成モード、生成日時。未生成／生成中／失敗を成功と区別する。

未合意：durationSecを目標時間と実経過時間のどちらとして使うか、時刻の保存表現、ID生成の所有者、enum名、自己申告と結果を一つの型へまとめるか。

## 提案3：保存と追記

1. 計測終了を受け取る。
2. 同一IDで計測結果を保存する。保存失敗を成功表示にしない。
3. 自己申告を入力した場合、同一IDへ追記する。
4. 合意済みの条件で履歴を取得・集計する。
5. レポートを生成し、同一IDへ追記する。

AI失敗でも保存済みの計測結果は保持し、定型文へ切り替える。更新は存在するIDへの更新とし、削除済みIDに対する遅延応答は再挿入しない。画面離脱・再生成時の古い応答を適用しないためのリクエスト識別や競合制御も利用側と合意する。

③へのAPI候補：計測結果の新規保存、自己申告更新、レポート更新、ID取得、履歴取得、削除。保存後の変更を一括upsertで扱うかは、削除済み記録の復活を防ぐ条件を先に確認する。

未合意：中断記録の保存・表示、入力せずに離脱した場合、生成再試行の更新規則、個別削除／全削除の範囲、保存失敗時の一時結果保持。

## 提案4：比較・通知

比較期間・最低件数・有効条件・当日結果の除外は未確定。中央値等はDartで計算し、AIへ数値の生成を任せない。未確定条件を固定値で実装しない。

通知はP1。④がOS制約を調査し、任意時刻・時刻変更・権限拒否・起動導線を①と調整する。通知拒否でP0を止めない。ユーザー指定の正式対象はCと同じiPhone 17 / iOS 27以降。手元のiPhone 15 / iOS 26.6.2は追加検証用とする。共有API・品質閾値の合意状況とは区別する。

## 並列作業への受け渡し

- ②：`lib/screens/` と `lib/widgets/` を実装。画面のコンストラクタと接続方法を①へ報告し、①がapp.dartの仮画面を置き換える。現行の開発用結果ルートには実測データがない。製品版では実在するID等を必須とする遷移契約を合意する。
- ③：共有契約の合意後にDB実装。依存追加とコード生成設定の要求を①へ渡す。
- ④：試験計画・読み取りレビューを先行。通知実装はP0の進捗を踏まえた着手指示後。
- ①：共有ファイル・依存・ネイティブ設定・STATEを管理。各担当の変更を無断でマージしない。

この基盤をBへ取り込んだ後に、②〜④はそのBから枝を切る。未コミットの基盤だけを前提に別worktreeで実装を始めない。
