# 実装開始前に決めること

以下は提供文書を読んで抽出した未決事項。選択肢・提案は仕様の確定を意味しない。該当機能の実装前にB・Cと人間が合意し、決定内容をここへ記録する。

## 最初の30分で固定する契約

1. **優先実機とOS**：機種・OS・利用可能なAIを確認する。AI不可でも定型文でデモ成功という文書の基準を共有する。
2. **計測時間の所有者**：分業書B-02はBがタイマーを扱い、C-02／計測APIはCが15秒計測を返す。実計測を終了する時計を一か所に置き、UI表示と同期する方式を決める。二重タイマーで別々に終了しない。
3. **結果と失敗の型**：概念モデルのqualityはgood／poor／interruptedだが、APIにはpermissionDenied等も必要。開始前失敗と計測結果をどう表すか、キャンセル方法も決める。
4. **時間・品質の記録**：durationSec:15という概念モデルで、途中中断の実経過時間をどう表すか。有効／無効の条件、明るさ・角度・安定性の閾値と判定期間も未確定。AIが適当な値を製品仕様として固定しない。
5. **保存と追記**：計測直後に保存し、その後の自己申告・体温・レポートを同一IDへどう反映するか。中断記録を履歴・比較へ含めるかも決める。
6. **比較の条件**：「過去7日程度」の期間、最低件数、有効記録の条件、当日結果の扱いを決める。未測定と実験心拍を通常の健康評価に混ぜない。
7. **削除と非同期更新**：全記録削除／個別削除の提供範囲、生成途中に削除した記録をAI応答で再作成しない扱いを決める。

## 仕様を読むときの注意

- アプリ仕様書は初回設定を含む6画面を列挙し、分業書は主要5画面をAの成果物としている。画面数の呼称にかかわらずP0の初回説明・権限導線を落とさない。
- 通知はP1。初回設定の通知拒否でP0を止めない。OS制約下での通知精度・翌日以降の更新方法は実装時に確認する。
- 両OS対応が目標でも、時間不足時に実機のあるOSへ集中する切替えが分業書で認められている。実際に保証するOSと未検証範囲を記録する。
